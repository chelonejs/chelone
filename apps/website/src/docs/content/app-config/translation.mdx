Chelone localizes through a small i18n instance you build with `createI18n` and
hand to `<Admin i18n={…}>`. A catalog is a flat map of keys to strings; every
key sits under `chelone.*`, whether a component translates it (page titles,
pagination, bulk-action labels, booleans, auth) or a core controller emits it
(save notifications, validation). An `<Admin>` with no `i18n` reads in English;
see [Without i18n](#without-i18n).

The components were ported from react-admin and kept its `ra.*` keys for a
while. They now read `chelone.*` with the same group names, so
`ra.page.list` is `chelone.page.list`. Nothing maps the old keys: a catalog that
still holds `ra.*` entries has no effect, and a component label you translated
under the old name needs the new one.

Four keys could not keep their name because a core controller already owns it
and says something else, so they keep the group and name their role. Their
English is unchanged:

| old key | new key |
| --- | --- |
| `ra.message.access_denied` | `chelone.message.access_denied_detail` |
| `ra.message.authentication_error` | `chelone.message.authentication_error_detail` |
| `ra.message.loading` | `chelone.message.loading_detail` |
| `ra.notification.http_error` | `chelone.notification.http_error_label` |

An app that writes its own catalog instead of spreading `englishMessages` can
mount `<I18nKeyEditor>` after the upgrade (see [Listing the missing
keys](#listing-the-missing-keys)): it lists every key the locale missed, which
is exactly the labels still holding their old name.

## Building the i18n instance

```tsx title="src/i18n.ts"
import { createI18n, defineMessages, englishMessages } from "@chelone/core";

const en = defineMessages({
  ...englishMessages, // every English chelone.* key
  "chelone.page.list": "All {name}", // override or add your own
});

export function makeI18n() {
  return createI18n({
    locale: "en",
    messages: { en },
    fallbackLocale: "en",
  });
}
```

`defineMessages` is an identity helper that gives you key/value type-checking.

## Typed keys, literal text and locale checks

`useTranslate()` types its keys and params against the catalog you register on
`Register.messages`, `literalMessages: true` makes `translate` return a key's
text instead of `string`, and `defineLocale` checks a locale catalog against a
base one. [Registering your app](/docs/type-safety/registering-your-app) is
where you write the key, and [Translations and
permissions](/docs/type-safety/translations-and-permissions) covers all three
and names the types behind them. This page is the runtime side.

## What ships in `englishMessages`

`englishMessages` is the English catalog: the component labels,
`defaultMessages` (the keys the core controllers emit: notifications,
validation, auth and loading messages) and `mapMessages` (the maps add-on's
labels). No entry repeats another. Spread it first, then add or override
entries. For another language, copy its keys and translate the values.

`defaultMessages` alone holds the controller keys only. Use it when you want to
write every component label yourself.

## Other languages

Each shipped catalog is its own export holding every `englishMessages` key, so
an app bundles only the languages it imports:

| locale | export |
| --- | --- |
| German (`de`) | `deMessages` |
| Mandarin Chinese, Simplified (`zh`) | `zhMessages` |
| Spanish (`es`) | `esMessages` |

```ts title="src/i18n.ts"
import { createI18n, englishMessages, zhMessages } from "@chelone/core";

export const i18n = createI18n({
  locale: "zh",
  messages: { en: englishMessages, zh: zhMessages },
  fallbackLocale: "en",
});
```

Spread one to override entries or add your own keys:
`{ ...zhMessages, "chelone.page.dashboard": "首页" }`.

The component labels are the keys the components pass to `translate`. Most call
it with an English default, so a missing key still reads as English (see
[Missing keys](#missing-keys-never-throw)). The keys, by group:

- `chelone.action.*`: `add`, `add_filter`, `back`, `bulk_actions`, `bulk_edit_apply`, `cancel`,
  `clear_input_value`, `clear_search`, `close_menu`, `confirm`, `create`,
  `delete`, `edit`, `export`, `list`, `move_down`, `move_up`, `open_menu`,
  `refresh`, `remove`, `remove_all_filters`, `remove_filter`, `save`, `search`,
  `select_all`, `select_row`, `show`, `toggle_theme`, `undo`, `unselect`,
  `update`
- `chelone.auth.*`: `logout`, `sign_in`, `sign_in_error`, `user_menu`
- `chelone.boolean.*`: `true`, `false`, `null`
- `chelone.input.*`: `file.upload_single`, `file.upload_several`,
  `image.upload_single`, `image.upload_several`, `password.toggle_hidden`,
  `password.toggle_visible`
- `chelone.message.*`: `access_denied_detail`, `auth_error`,
  `authentication_error_detail`,
  `bulk_delete_content`, `bulk_delete_title`, `bulk_edit_description`,
  `bulk_edit_nested_source`, `bulk_update_content`, `bulk_update_title`,
  `delete_content`, `delete_title`, `error`, `loading_detail`
- `chelone.navigation.*`: `next`, `no_results`, `page_range_info`,
  `page_rows_per_page`, `partial_page_range_info`, `previous`
- `chelone.notification.*`: `application_update_available`, `http_error_label`,
  `offline`
- `chelone.page.*`: `access_denied`, `authentication_error`, `create`, `dashboard`,
  `error`, `list`, `loading`
- `chelone.saved_queries.*`: `new_label`, `query_name`, `remove_label_with_name`

search the source for `translate("chelone.`.

## Interpolation and plurals

Chelone uses **single-brace** interpolation — `{name}` — **not** react-admin's
`%{name}`:

```ts
"chelone.page.create": "Create {name}",
"chelone.navigation.page_range_info": "{offsetBegin}-{offsetEnd} of {total}",
```

Plurals are an object keyed by `Intl.PluralRules` categories (not react-admin's
`a |||| b`). `other` is required:

```ts
"chelone.action.bulk_actions": {
  one: "1 item selected",
  other: "{count} items selected",
},
```

The form is picked from the `count` param, or `smart_count` (the name
react-admin and the components use) when `count` is absent. Whichever you pass
also fills `{count}` and `{smart_count}` in the text:

```ts
i18n.translate("chelone.action.bulk_actions", { count: 1 }); // "1 item selected"
i18n.translate("chelone.action.bulk_actions", { count: 4 }); // "4 items selected"
```

Without a numeric count, the `other` form is used. A category the locale needs
but the message lacks (for example `few` in Polish) falls back to `other`.

## Missing keys never throw

If a key isn't in the catalog, `translate` returns the key itself (or a `_`
string fallback) — it never throws. A `_` fallback is interpolated with the same
params, and most components pass one, so labels such as "Cancel" or "Refresh"
read as English without a catalog entry:

```ts
translate("chelone.action.cancel", { _: "Cancel" }); // "Cancel" when the key is missing
```

Where a component passes no `_`, a catalog that lacks the key shows the raw
`chelone.page.list`-style key. `englishMessages` covers the keys the components
translate; a catalog that does not spread it needs the keys you see.

### Listing the missing keys

`<I18nKeyEditor>` lists the keys the current locale missed and exports what you
type as JSON. Create a store, pass `store.record` as `onMissingKey`, and mount
the panel with that store:

```tsx title="src/i18n.ts"
import { createI18n, createMissingKeyStore } from "@chelone/core";

export const missingKeys = createMissingKeyStore();

export const i18n = createI18n({
  locale: "fr",
  messages: { en, fr },
  onMissingKey: missingKeys.record,
});
```

```tsx
<I18nKeyEditor store={missingKeys} />
```

A key counts as missing even when it has a `_` fallback or the fallback locale
holds it. The export is flat JSON to spread into a catalog. See
[I18nKeyEditor](/docs/ui-layout/i18n-key-editor).

## Without i18n

`i18n` is optional on `<Admin>`. Without it, `<Admin>` builds one instance from
`englishMessages` with locale `en`, so a list's heading reads "Posts", not
`chelone.page.list`. An `i18n` you pass is used as is, with no English merged in:
spread `englishMessages` into your catalog to extend it.

A component mounted outside `<Admin>` has no instance, so `useTranslate()`
echoes: a key with no `_` default comes back as the key, and a key with one
renders the default with placeholders filled in. In React, the built-in
`<LoginPage>` supplies its own English catalog (`defaultMessages`) and
notification store for its subtree.

## Multiple locales

Register more catalogs under `messages` and switch at runtime:

```tsx
createI18n({
  locale: "en",
  messages: { en, fr },
  fallbackLocale: "en",
});
```

Read and change the active locale from your components:

```tsx
import { useTranslate, useLocale, useSetLocale } from "@chelone/react";

const translate = useTranslate();   // translate("chelone.action.save")
const locale = useLocale();         // "en"
const setLocale = useSetLocale();   // setLocale("fr")
```

## Bring your own engine

`<Admin i18n>` takes any object that satisfies `I18nProvider`, exported from
`@chelone/core`. `createI18n` is one implementation of it; an adapter over
i18next, Lingui or your own engine works as long as it honours the same
conventions. The adapters type their `i18n` prop as `AnyCheloneI18n`, an alias of
`I18nProvider`, so the props tables show `I18nProvider`.

| member | what it must do |
| --- | --- |
| `translate(key, params?)` | the message for `key`, interpolated and pluralized; never throws |
| `getLocale()` | the active locale, as a BCP 47 tag |
| `setLocale(locale)` | make `locale` active and notify each subscriber once |
| `getLocales()` | every locale the provider can translate |
| `subscribe(callback)` | register a locale-change callback and return its unsubscribe |

What `translate` owes the components:

- Placeholders are single-brace `{name}`, filled from `params`. A placeholder
  with no matching param is left as written.
- A key no catalog holds comes back as the key itself, and `translate` never
  throws.
- A string `_` param is the default text for a missing key, and only for one: a
  key the catalog holds ignores it. The default is interpolated with the same
  params.
- The plural count is `count`, or `smart_count` when `count` is absent; `count`
  wins when both are given. Whichever one is used also fills `{count}` and
  `{smart_count}` in the text.
- Plurals are `{ one, other }` objects keyed by `Intl.PluralRules` categories
  for the active locale, so a locale with more than two forms gets its own
  (`few` in Polish). `other` is required, and stands for a category the message
  lacks and for a message with no count.

`onMissingKey` and the throw on an unregistered locale are `createI18n` options,
not part of the contract: an engine such as i18next has its own answers to both.

A provider of your own, in full:

```ts title="src/i18n.ts"
import type { I18nProvider } from "@chelone/core";

type Message = string | ({ other: string } & Record<string, string>);

const catalogs: Record<string, Record<string, Message>> = {
  en: { "chelone.action.save": "Save", "app.greeting": "Hello {name}" },
  fr: { "chelone.action.save": "Enregistrer", "app.greeting": "Bonjour {name}" },
};

let locale = "en";
const subscribers = new Set<() => void>();

function fill(text: string, params?: Record<string, string | number>): string {
  return text.replace(/\{(\w+)\}/g, (match, name: string) =>
    params && name in params ? String(params[name]) : match,
  );
}

export const i18n: I18nProvider = {
  translate(key, params) {
    const message = catalogs[locale]?.[key];
    if (message === undefined) {
      return typeof params?._ === "string" ? fill(params._, params) : key;
    }
    if (typeof message === "string") return fill(message, params);
    const raw = params?.count ?? params?.smart_count;
    const count = Number(raw);
    if (Number.isNaN(count)) return fill(message.other, params);
    const form =
      message[new Intl.PluralRules(locale).select(count)] ?? message.other;
    // Whichever name carried the count fills both {count} and {smart_count}.
    return fill(form, {
      ...params,
      count: params?.count ?? raw,
      smart_count: params?.smart_count ?? raw,
    });
  },
  getLocale: () => locale,
  setLocale(next) {
    if (next === locale) return;
    locale = next;
    for (const notify of subscribers) notify();
  },
  getLocales: () => Object.keys(catalogs),
  subscribe(notify) {
    subscribers.add(notify);
    return () => void subscribers.delete(notify);
  },
};
```

The repo runs the list above as a suite, `testI18nProviderContract`, and runs it
against `createI18n` itself. It lives in `@chelone/test-utils`, a private
workspace package that is not published and imports nothing from Chelone, so
copy it into your repo and hand it your factory:

```ts
import { testI18nProviderContract } from "./test/i18n-provider-contract";

testI18nProviderContract((options) => myI18n(options));
```

It pins plain lookup, interpolation, the key echo, the `_` default, `count` and
`smart_count`, a locale with more than `one` and `other`, `getLocale`,
`getLocales`, `setLocale` and the subscribers. A provider that ignores the `_`
default, or that notifies for a locale already active, fails it.

### With i18next

A team that already runs i18next, with its backends and tooling, can wrap that
instance instead. `i18next` is an optional peer of `@chelone/utils/i18next`:

```bash
pnpm add @chelone/utils i18next
```

```ts title="src/i18n.ts"
import { englishMessages } from "@chelone/core";
import {
  createI18nextProvider,
  toI18nextResource,
} from "@chelone/utils/i18next";
import i18next from "i18next";

const instance = i18next.createInstance();
await instance.init({
  lng: "en",
  resources: {
    en: { translation: toI18nextResource(englishMessages) },
  },
});

export const i18n = createI18nextProvider(instance);
```

```tsx
<Admin i18n={i18n} />
```

- `toI18nextResource` turns a Chelone catalog into an i18next bundle: a string
  entry is copied, and a `{ one, other }` entry becomes `key_one` and
  `key_other`, with a suffix for every other `Intl.PluralRules` category.
- `{name}` placeholders are set per call, so the instance keeps its own
  `{{name}}` interpolation for the rest of your app. Values are not
  HTML-escaped, as in `createI18n`.
- `setLocale` calls `changeLanguage` and expects it to settle at once, which it
  does for resources already in memory. With a lazy backend, load the language
  through i18next first, then call `setLocale`.
- A missing key returns the key, and a string `_` param is the default text, as
  the contract says.

## Right to left

`<Admin>` sets `dir` on `<html>` from the active locale, in both adapters, so a
right-to-left locale renders right to left and switching back to `en` renders
left to right again. The rule behind it is `getLocaleDirection(locale)`,
exported from `@chelone/core`, so your own markup can follow it:

```ts
import { getLocaleDirection } from "@chelone/core";

getLocaleDirection("ar"); // "rtl"
getLocaleDirection("ar-EG"); // "rtl"
getLocaleDirection("pa-Arab"); // "rtl"
getLocaleDirection("pa-Guru"); // "ltr"
getLocaleDirection("en"); // "ltr"
```

A tag's script subtag decides over its language, so Punjabi in Arabic script is
right to left and Punjabi in Gurmukhi is not. `<Admin>` builds an English i18n
when you pass none, so it sets `dir="ltr"`; only React's low-level
`<AdminContext>` with no `i18n` leaves `dir` as the host set it.

## Translatable records

Catalogs localize the interface. To localize the data, a translatable record
stores `{ en, fr }` under each translated field, for example
`{ name: { en: "Chair", fr: "Chaise" } }`. Edit those fields with
[TranslatableInputs](/docs/editing/translatable-inputs) and show them with
[TranslatableFields](/docs/viewing/translatable-fields). Both take the list of
locales to show; the app locale only picks the tab selected first.

## Tips

- `setLocale` throws on an **unregistered** locale — register every locale in
  `messages` before switching to it.
- Keep the interpolation single-brace (`{name}`) — porting react-admin catalogs
  means rewriting `%{name}` → `{name}` and `a |||| b` → `{ one, other }`.
- Register the catalog under `Register.messages` and `useTranslate()` types its
  keys and params across the app (see [Translations and
  permissions](/docs/type-safety/translations-and-permissions)).

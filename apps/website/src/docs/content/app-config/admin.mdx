`<Admin>` is the root of a Chelone app. It layers the whole provider stack — the
**data provider**, the **query client**, optional **i18n**, **notifications**,
**store**, **auth**, and the **resource registry** — then renders the resources
and routes you declare as children. It joins the router your app already runs, or
creates its own, so a wrapper router is optional.

## A live admin

The reference admin, running in a frame: a sidebar menu, an app bar, and the
`posts` resource with its list, create, edit and show views. Everything in it
comes from one `<Admin>` and a few `<Resource>` markers.

## The minimal admin

```tsx title="src/App.tsx"
import { fakeDataProvider } from "@chelone/core";
import { Admin, Layout, Resource } from "@chelone/react";
import { QueryClient } from "@tanstack/react-query";
import { PostList } from "./posts";

const queryClient = new QueryClient();
const dataProvider = fakeDataProvider({ posts: [] });

export function App() {
  return (
    <Admin dataProvider={dataProvider} queryClient={queryClient}>
      <Admin.Layout>
        <Layout />
      </Admin.Layout>
      <Resource name="posts" list={PostList} />
    </Admin>
  );
}
```

`dataProvider` and `queryClient` are the only required props. The rest are opt-in
services you add as the app grows. With no host router, `<Admin>` creates a
browser router for you.

## The full stack

A production admin configures the optional services too — the i18n catalog, the
notification store the toaster reads, and the KV store for list scroll and
preferences:

```tsx
import {
  createNotificationStore,
  createStore,
  fakeDataProvider,
} from "@chelone/core";
import { Admin, Layout, Resource } from "@chelone/react";
import { QueryClient } from "@tanstack/react-query";
import { makeI18n } from "./i18n";
import { PostEdit, PostList } from "./posts";
import { resources } from "./resources";

const queryClient = new QueryClient();
const dataProvider = fakeDataProvider({ posts: [] });
const i18n = makeI18n();
const notifications = createNotificationStore();
const store = createStore();

export function App() {
  return (
    <Admin
      dataProvider={dataProvider}
      queryClient={queryClient}
      i18n={i18n}
      notifications={notifications}
      store={store}
      resources={resources}
    >
      <Admin.Layout>
        <Layout />
      </Admin.Layout>
      <Resource name="posts" list={PostList} edit={PostEdit} />
    </Admin>
  );
}
```

## The `resources` prop and schema validation

Pass a resource registry built with `defineResources({ posts: { schema } })` as
`resources` to enable **automatic form validation** — the form controllers read
each resource's Zod schema and validate against it on submit. See
[Resource](/docs/app-config/resource) for the registry.

## The layout slot

`<Admin.Layout>` is the opt-in shell: sidebar, app bar, toaster. Omit it for a
headless admin, or pass your own layout element. Other slots (`<Admin.Dashboard>`,
`<Admin.LoginPage>`, and the auth/error pages) follow the same pattern.

Each slot also has a prop of the same lowercase name (`layout`, `dashboard`,
`loginPage`, `catchAll`, and so on). When both are given, the prop wins over the
slot child:

```tsx
import { Admin, Resource } from "@chelone/react";
import { Home, OldHome } from "./home";
import { dataProvider, queryClient } from "./providers";
import { PostList } from "./posts";

export function App() {
  return (
    <Admin
      dataProvider={dataProvider}
      queryClient={queryClient}
      dashboard={<Home />}
    >
      <Admin.Dashboard>
        <OldHome />
      </Admin.Dashboard>
      <Resource name="posts" list={PostList} />
    </Admin>
  );
}
```

Here `<Home />` renders at the index route and `<OldHome />` never does.

## Auth, basename and permissions

- `requireAuth` gates the whole shell on `authProvider`. While the auth check is in
  flight the loading page shows, never the layout. An unauthenticated visitor gets
  the login page. Without an `authProvider` the gate is open.
- `basename` is the URL prefix the app is served under. A router `<Admin>` creates
  applies it, so links and redirects come out prefixed once. Under a host router,
  set it to the path the host mounts `<Admin>` at, relative to the host router's
  own `basename`, and Chelone prepends it to the links it builds.
- The children can be a function that receives the `permissions` prop, so resources
  can depend on who is signed in. It may return a promise, and the loading page
  shows until it resolves. A `ready` slot, if you set one, shows in its place
  during that wait.

```tsx title="src/App.tsx"
import { Admin, Resource } from "@chelone/react";
import { authProvider, dataProvider, queryClient } from "./providers";
import { PostList } from "./posts";
import { UserList } from "./users";

export function App({ permissions }: { permissions: string }) {
  return (
    <Admin
      dataProvider={dataProvider}
      queryClient={queryClient}
      authProvider={authProvider}
      requireAuth
      permissions={permissions}
    >
      {(role) => (
        <>
          <Resource name="posts" list={PostList} />
          {role === "admin" ? (
            <Resource name="users" list={UserList} />
          ) : null}
        </>
      )}
    </Admin>
  );
}
```

## Route-less admin

`<Admin>` mounts its own route table by default. A file-routed app owns its URLs
and wants a loader per route, so pass `routes={false}`. `<Admin>` then renders
the layout, the auth gate and the shell error boundary around the router's
`<Outlet>`, and your route fills it with a Chelone page.

```tsx title="app/routes/admin.tsx"
import { Admin, Layout, Resource } from "@chelone/react";
import { authProvider, dataProvider, queryClient } from "../providers";

export default function AdminRoute() {
  return (
    <Admin
      routes={false}
      basename="/admin"
      dataProvider={dataProvider}
      queryClient={queryClient}
      authProvider={authProvider}
      requireAuth
    >
      <Admin.Layout>
        <Layout />
      </Admin.Layout>
      <Resource name="posts" hasList hasEdit />
    </Admin>
  );
}
```

```tsx title="app/routes/admin.posts.tsx"
import { DataTable, List } from "@chelone/react";

export default function Posts() {
  return (
    <List resource="posts">
      <DataTable>
        <DataTable.Col source="title" />
      </DataTable>
    </List>
  );
}
```

- `<Resource>` children still register, so the menu, `useResourceDefinition`, the
  record representation and the create and edit buttons work. Their views are not
  mounted: your routes render `List`, `Create`, `Edit` and `Show`, each given its
  `resource`. `Edit` and `Show` read the route's `:id` param when given no `id`.
- Chelone builds links as `/posts`, `/posts/create`, `/posts/:id` and
  `/posts/:id/show` under `basename`, so route your files to those paths.
- `<Admin>` owns no path: it adds no catch-all, index redirect or dashboard
  route. The `catchAll` and `dashboard` slots do nothing, and the menu has no
  Dashboard entry.
- `<CustomRoutes>` and the `authCallback` slot do nothing either, since your app
  routes those paths.
- A server render shows an empty menu until hydration, because resources register
  in an effect.

## Swapping the router

`<Admin>` defaults to the react-router adapter. Pass a different adapter on
`router` to run under another router. The components speak the adapter's
navigation contract, not a specific router.

`@chelone/react/tanstack-router` ships two TanStack Router adapters. Pick one by
who owns the router:

- `tanstackRouterAdapter` creates its own TanStack router on memory history, so
  the browser URL bar does not follow navigation. Pick it for an app with no
  TanStack router, or to try the seam. It is a reference adapter, not a second
  maintained router.
- `tanstackHostRouterAdapter` joins the router of the nearest TanStack
  `RouterProvider`, such as a TanStack Start app's, and reads and drives its URL.
  Pick it when `<Admin>` mounts under one of the app's routes. It never creates a
  router, so outside a `RouterProvider` it throws TanStack's own error.

Under a splat route such as `/admin/$`, pass the mount path as `basename`:

```tsx title="src/routes/admin.$.tsx"
import { Admin, Resource } from "@chelone/react";
import { tanstackHostRouterAdapter } from "@chelone/react/tanstack-router";
import { createFileRoute } from "@tanstack/react-router";
import { dataProvider, queryClient } from "../admin";
import { PostList } from "../posts";

export const Route = createFileRoute("/admin/$")({
  component: () => (
    <Admin
      dataProvider={dataProvider}
      queryClient={queryClient}
      router={tanstackHostRouterAdapter}
      basename="/admin"
    >
      <Resource name="posts" list={PostList} />
    </Admin>
  ),
});
```

With `tanstackRouterAdapter`, custom routes must use the adapter's own `Route`,
not react-router's:

```tsx title="src/App.tsx"
import { fakeDataProvider } from "@chelone/core";
import { Admin, CustomRoutes, Layout, Resource } from "@chelone/react";
import { tanstackRouterAdapter } from "@chelone/react/tanstack-router";
import { QueryClient } from "@tanstack/react-query";
import { PostList } from "./posts";
import { SettingsPage } from "./settings";

const queryClient = new QueryClient();
const dataProvider = fakeDataProvider({ posts: [] });
const { Route } = tanstackRouterAdapter;

export function App() {
  return (
    <Admin
      dataProvider={dataProvider}
      queryClient={queryClient}
      router={tanstackRouterAdapter}
    >
      <Admin.Layout>
        <Layout />
      </Admin.Layout>
      <Resource name="posts" list={PostList} />
      <CustomRoutes>
        <Route path="/settings" element={<SettingsPage />} />
      </CustomRoutes>
    </Admin>
  );
}
```

The adapters live on their own entry so `@chelone/react` loads without
`@tanstack/react-router`, an optional peer. Install that peer only when you use
either adapter.

### Revalidating a server-rendered route

A client component under a server-rendered route calls `useRevalidate()` after a
write, so the router fetches that route's data again. The adapter decides how:

- Both TanStack adapters call `router.invalidate()`, which re-runs the matched
  routes' loaders.
- An adapter with no `useRevalidate`, such as the react-router default, gets a
  `replace` navigation to the current path, search, hash and state. State
  outside the route survives, since the page does not reload.

```tsx title="src/posts/publish-button.tsx"
import { useRevalidate, useUpdate } from "@chelone/react";

export function PublishButton({ id }: { id: number }) {
  const update = useUpdate("posts");
  const revalidate = useRevalidate();
  return (
    <button
      type="button"
      onClick={() =>
        update.mutate({ id, data: { published: true } }, { onSuccess: revalidate })
      }
    >
      Publish
    </button>
  );
}
```

An app's own adapter adds the optional `useRevalidate(): () => void` member to
plug in its router's refresh, such as Next.js's `router.refresh()`.

## Tips

- With the default react-router adapter, `<Admin>` joins a router above it
  (`<BrowserRouter>`, or your framework's router) and creates its own browser
  router when there is none.
- Create the `QueryClient` and the data provider at module scope (stable across
  renders), not inside the component body.

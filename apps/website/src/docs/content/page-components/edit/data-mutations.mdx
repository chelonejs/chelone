title: "Data Mutations"
description: "How Edit saves — validation, the update call, and cache reconciliation."
---

Saving an `<Edit>` form runs a pipeline: **validate → persist → reconcile**. The
edit-form controller owns it; the `<Toolbar>`'s Save button (or a bare
`<SaveButton>`) fires it.

## The save pipeline

1. **Validate.** The form values are checked against the resource's Zod schema
   (if one is registered) plus any per-input `validate` functions. On failure,
   the messages surface on the inputs and the save is blocked.
2. **Persist.** The controller calls the data provider's `update(resource, {
   id, data, previousData })` and awaits the result.
3. **Reconcile.** On success, the updated record is written back into the
   TanStack Query cache, a save notification fires, and the form resets to the
   saved values.

## Mutation hooks

Under the hood the controller uses `useUpdate`, one of the mutation hooks you can
call directly for custom flows (an inline toggle, a bulk action, a button
outside a form). Each hook binds a resource and returns a TanStack Query
mutation object — call `.mutate` (or `.mutateAsync`) with the data-provider
params:

```tsx
import { useUpdate } from "@chelone/react";

function PublishButton({ id }: { id: number }) {
  const { mutate, isPending } = useUpdate("posts");
  return (
    <button
      disabled={isPending}
      onClick={() => mutate({ id, data: { published: true } })}
    >
      Publish
    </button>
  );
}
```

The full set: `useCreate`, `useUpdate`, `useDelete` for writes, and `useGetOne`,
`useGetList`, `useGetMany`, `useGetManyReference`, and `useGetManyAggregate` for
reads — each a thin, typed wrapper over the data
provider plus the query cache. For a fully-typed set bound to your registry, call
`createCheloneHooks<typeof resources>()` once and use its members.

## Deleting

The `<Toolbar>` includes a confirm-gated Delete on Edit views. To delete
elsewhere, use `<DeleteButton>` (which wraps `useDelete` behind a confirm
dialog) or call `useDelete` yourself.

## Tips

- The data provider owns the actual persistence — REST, GraphQL, Supabase,
  in-memory. The mutation hooks and `<Edit>` only speak its `update` / `delete`
  contract.
- Validation errors returned by the provider (a rejected `update`) surface on
  the form the same way schema errors do.

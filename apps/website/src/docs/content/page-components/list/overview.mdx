The `<List>` view is where users browse a resource. It runs the list controller
for the ambient `<Resource>`, fetches the current page of records, and publishes
them through a **list context** that every descendant reads: the `<DataTable>`,
the pagination, the filter bar. You compose what to show; `<List>` owns the
fetch and the URL-synced query state (page, sort, filters).

## A live list

Here is the `posts` list, running against the in-memory provider: a real
`<DataTable>` over 30 seeded records, paged ten at a time by `<ListPagination>`.

<ComponentPreview name="page-components/list/basic" />

```tsx title="src/posts.tsx"
import {
  BooleanField,
  DataTable,
  EditButton,
  List,
  ListPagination,
  ReferenceField,
  TextField,
} from "@chelone/react";

export function PostList() {
  return (
    <List>
      <DataTable>
        <DataTable.Col source="title" />
        <DataTable.Col label="Author">
          <ReferenceField source="author_id" reference="authors">
            <TextField source="name" />
          </ReferenceField>
        </DataTable.Col>
        <DataTable.NumberCol source="views" />
        <DataTable.Col source="published">
          <BooleanField source="published" />
        </DataTable.Col>
        <DataTable.Col>
          <EditButton />
        </DataTable.Col>
      </DataTable>
      <ListPagination />
    </List>
  );
}
```

`<List>` renders only what you give it. Without
[`<ListPagination>`](/docs/viewing/list-pagination) the list stays on page 1 and
the user cannot reach the other pages or change the page size.

Wire it onto the resource so `/posts` renders it:

```tsx
import { Resource } from "@chelone/react";
import { PostList } from "./posts";

<Resource name="posts" list={PostList} />;
```

Clicking a row opens its edit page: `<DataTable>` defaults `rowClick` to
`"edit"`. Pass `rowClick="show"`, a path, a function, or `false` to change it.

## How it works

`<List>` reads the resource from the surrounding `<Resource>` context (or from a
`resource` prop) and calls `useListController`. The controller keeps the query
(current page, `perPage`, sort, and the active filters) in sync with the URL, so
a shared link reproduces the exact view. The fetched records, the loading flag,
and the selection are handed to the descendants through the list context; the
`<DataTable>` renders the rows, and its column headers drive sorting.

## Props

<PropsTable name="List" />

`<List>` takes `resource`, `perPage`, `title`, `actions`, `component`,
`className` and `children`. Nothing else is forwarded to the controller. For
anything more (default filters, a permanent filter, a default sort, a
different store key) call `useListController` yourself and provide the result
with `ListContextProvider`. `ListView` is the same title, actions and body
layout `<List>` renders. It reads the resource from context, not from the
controller, so render the component inside a `<Resource>` or a
`ResourceContextProvider`, or `ListView` throws:

```tsx title="src/posts.tsx"
import {
  DataTable,
  ListContextProvider,
  ListPagination,
  ListView,
  useListController,
} from "@chelone/react";

export function PublishedPostList() {
  const controller = useListController("posts", {
    perPage: 25,
    sort: { field: "views", order: "DESC" },
    filterDefaultValues: { published: true },
  });

  return (
    <ListContextProvider value={controller}>
      <ListView title="Published posts">
        <DataTable>
          <DataTable.Col source="title" />
          <DataTable.NumberCol source="views" />
        </DataTable>
        <ListPagination />
      </ListView>
    </ListContextProvider>
  );
}
```

See [Advanced](/docs/page-components/list/advanced) for every controller
option. For a feed that appends pages instead of replacing them, use
[`<InfiniteList>`](/docs/page-components/list/infinite-list).

## URL sync

The controller writes the list query to the URL and reads it back, so a list is
a link you can share.

- On by default for a top-level list, and active whenever the list renders
  under a router (inside `<Admin>` it does). Pass
  `useListController("posts", { syncWithLocation: false })` for an embedded or
  reference list that should keep its query out of the URL.
- The params are `filter` and `displayedFilters` (both JSON), `sort`, `order`
  (`ASC` or `DESC`), `page` and `perPage`. Malformed values are ignored. The URL
  carries the primary sort only.
- Opening a URL that carries a custom param seeds the first fetch from it. A
  param is custom when it sets a filter with at least one key, a `sort` or
  `order`, a `perPage`, or a `page` other than 1. A URL without one, such as
  `/posts`, `/posts?page=1`, `/posts?filter={}` or one with only
  `displayedFilters`, is treated as clean: the saved params, then the defaults,
  apply, even though the address bar shows the URL.
- A change to page, sort, filters or page size replaces the current history
  entry. It does not push a new one, so the back button leaves the list rather
  than stepping through each page or keystroke. The mount itself writes nothing:
  a clean URL stays clean until the user changes something.
- If the location changes after the list has mounted (a followed link, or back
  and forward between two URLs of the same list) a URL with custom params
  re-seeds the list from it. A URL without any leaves the list as it is, so
  following a plain link to `/posts` does not reset a filtered list.
- The params are also saved in the store under `<resource>.listParams`. When the
  URL carries no list params, the list restores the saved ones, then falls back
  to the options (`perPage`, `sort`, `filterDefaultValues`). Pass
  `storeKey: "other"` to namespace them, or `storeKey: false` to turn the
  persistence off.

### Prefetch in a route loader

A loader that prefetches a list has to hit the query key the mounted list
observes. `listFetchParams` builds those params from the same code the
controller uses: the option defaults, then the saved params, then the URL, with
the permanent `filter` merged over the filter.

```ts
import { getListOptions, listFetchParams } from "@chelone/core";

export async function loader({ request }: { request: Request }) {
  const { search } = new URL(request.url);
  const params = listFetchParams(ctx, "posts", { perPage: 20 }, search);
  await ctx.queryClient.fetchQuery(getListOptions(ctx, "posts", params));
}
```

Pass the same options the list gets. `search` is the raw query string, with or
without the `?`.

A mount takes the same `search` as its fourth argument, so the loader's key and
the list's first fetch are one key. `<List>` and `useListController` pass it
from the router location; a vanilla mount passes it itself:

```ts
const controller = createListController(ctx, "posts", { perPage: 20 }, search);
```

The prefetched page is also what the controller's FIRST snapshot holds, which is
what a server render reads before anything subscribes. A snapshot never keeps
the rows of params it has moved off.

- A server has no saved list params. A server loader passes a `ctx` with no
  `store`, so the params are the defaults plus the URL. A browser that holds
  saved params and opens a clean URL mounts the list on a different key and
  fetches again. To get the same key on both sides, set `storeKey: false` on the
  list or keep the URL canonical. A loader that runs in the browser passes the
  `ctx` with its store and matches.
- The loader's `QueryClient` needs a `staleTime` above 0, as dehydrate and
  hydrate do. At 0 a mounted list refetches the entry the loader just loaded.

## Tips

- A `<List>` **must** be inside a `<ResourceContextProvider>` (a `<Resource>`
  supplies one) or be given an explicit `resource` prop, or it throws.
- The children are usually a `<DataTable>` and a `<ListPagination>`, but any
  component that reads the list context works. Build your own layout on top of
  `useListContext`.
- `perPage` sets the initial page size. A page size the user picked, or one in
  the URL, wins over it.
